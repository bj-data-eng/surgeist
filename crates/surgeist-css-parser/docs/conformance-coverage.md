# Syntax 3 conformance coverage

This page maps the clauses of the pinned CSS Syntax Module Level 3 edition to
the tests of this crate. It records what the tests establish and what they do
not, so a reader can tell a covered clause from an unexamined one.

**Only the rows marked "Claimed" or "Claimed in part" are claimed.** Every
other row has the status "Not claimed": its clause has no implementation or no
test in this crate yet. A row changes only in the commit that adds the
implementation and the tests that exercise its clause, and that commit cites the
tests by name. Browser conformance is not claimed anywhere on this page.

## Edition and evidence classes

The [CSS Syntax 3 edition](../../../references/SOURCE-EDITIONS.md#css-syntax-3-edition)
selected for Surgeist is the 1 October 2026 Candidate Recommendation Draft. Its
[local copy][syntax] is the only source of expected behavior for these rows.
The conventions of other libraries are not an authority for a clause.

Each covered row will name its evidence by class:

- **Specification-derived**: a literal input and expected output written from
  the clause text or one of its examples.
- **Differential**: a comparison with another implementation's output on the
  same input. It detects disagreement; it never establishes a clause, and a
  disagreement is resolved from the specification text.
- **Property**: an invariant checked over generated inputs.
- **External vectors**: a retained corpus of third-party conformance tests,
  with its provenance recorded with the corpus.

## Clause map

Tests named without a path are in `tests/lexer.rs`, except in the rows of
sections 5.2, 5.3 and 5.5.7 to 5.5.10, where a name is in `tests/document.rs` or
`tests/stream.rs` as the row says, and in the rows of sections 5.4, 5.5.1 to
5.5.6 and 5.5.8, where it is in `tests/grammar.rs`, those of sections 5.5.11, 6
and 9, where it is in `tests/unicode_range.rs`, `tests/anb.rs` and
`tests/serialize.rs`. `properties.rs`, `syntax_properties.rs`,
`document_properties.rs`, `protocol.rs`, `token.rs`, `metering.rs` and
`cssparser_oracle.rs` are in `tests/` too, and tests in `src/` are named by
their file.

All in `tests/lexical.rs`. Each counts the members of its class over every
Unicode scalar value and compares the count with the number the clause's ranges
imply, so a class with an extra member fails as surely as one missing a member.

- Digit: `digit_is_exactly_u0030_to_u0039_inclusive`,
  `digit_excludes_non_ascii_decimal_digits`.
- Hex digit: `hex_digit_is_digit_or_a_to_f_in_either_case`.
- Uppercase letter, lowercase letter, letter:
  `uppercase_letter_is_exactly_u0041_to_u005a_inclusive`,
  `lowercase_letter_is_exactly_u0061_to_u007a_inclusive`,
  `letter_is_an_uppercase_or_a_lowercase_letter_and_nothing_else`.
- Ident-start code point and ident code point (with the 2021 non-ASCII rule):
  `ident_start_is_a_letter_a_non_ascii_ident_code_point_or_low_line`,
  `ident_code_point_is_an_ident_start_a_digit_or_hyphen_minus`.
- Non-printable code point:
  `non_printable_is_u0000_to_u0008_u000b_u000e_to_u001f_and_u007f`,
  `non_printable_excludes_the_control_code_points_that_are_whitespace_or_form_feed`.
- Newline and whitespace:
  `newline_is_only_u000a_because_preprocessing_converts_cr_and_ff`,

U+007F ends an ident (28 cases), and the five whitespace code points read as
whitespace while 26 others do not (`whitespace.html`, 31 cases).

### WPT css-syntax vectors

The corpus [tests/corpus/wpt](../tests/corpus/wpt/README.md) holds 22 of the 23
`css/css-syntax` tests that the pinned edition cites outside
`css/css-syntax/charset/`, at WPT commit `ddcca5943fd41232d42149aaa19d9a04c5651b18`
(committed 2026-09-10), with the upstream license. Each of the 23 was looked up
at that commit: 22 were present and `parse-invalid-input.html` returned HTTP 404,
so it is recorded as absent and nothing is adapted from it. The commit predates
the 1 October 2026 edition, so a test added to the suite after 2026-09-10 would
not be here. The 21 `charset/*` tests are not acquired, and section 3.2 has no
WPT backing.

The evidence class is external vectors. Each vector is a reviewed literal
adaptation bound to its upstream path, the SHA-256 digest of the raw file, a

The vectors state what the algorithms return. The crate reports a construct that
an algorithm drops ("return nothing") as a failed unit so that a host can say
what was dropped, and the vectors do not claim those reports; they describe
accepted units and invalid rule errors. Whether a rule or declaration is valid
is the grammar's decision and is an input of a case.

### Readings the tests record

- Section 4.3.8 returns true when the second code point is EOF, because EOF is
  not a newline and the section returns false only for a newline. Section
  4.3.7's EOF branch ("consume an escaped code point") exists for that case.
  The "Changes from the 20 February 2014 Candidate Recommendation" entry that
  calls a final backslash "not a valid escape" contradicts the normative text;
  the normative text governs.
- The checks and classes describe code points after input preprocessing (3.3),
  as the specification's "newline" definition says: only U+000A is a newline,
  and U+000D and U+000C are ordinary code points to these functions.
- Section 4.3.6 words the bad url that follows whitespace without "this is a
  parse error", and section 4.3.15 words EOF without one, so the lexer reports
  no event for them even though the token is a `<bad-url-token>`.
- Section 4.3.4 leaves the interval of the whitespace between `url(` and a quote
  unstated; the lexer reports one whitespace token covering the whole run the
  clause consumes, and the function token ends at the parenthesis.
- Section 9 says the tokenizer produces no comment token. The lexer reports each
  comment as a `Comment` token, which a consumer ignores like whitespace; this is
  the one extension, and consecutive comments are consecutive tokens.
- Section 5.5.5 returns "rules" at the end of the contents or at a `}` without
  appending the declarations collected since the last rule. Read literally that
  drops a trailing run of declarations, which cannot be meant: the iterators
  report every declaration and rule, the final run included, and leave the
  grouping to the consumer.
- Section 5.5.6 step 8 asks, for `unicode-range`, for the text "corresponding to
  the tokens returned by the consume a list of component values call", which
  includes the `!important` that step 6 has already taken into a flag. The
  declaration offers the text of the value after steps 6 and 7.
- Section 5.5.3 returns nothing, without an error, for a rule that looks like a
  custom property. Where a declaration of the same text was first rejected by
  the grammar, the unit is reported as that failed declaration, so the
  grammar's verdict is not lost.
- Section 9's table does not list a `<` and a `!` followed by two hyphens (a
  CDO-token when written plainly) or the ident `--` followed by `>` (a
  CDC-token); the round-trip requirement needs a comment in both, found by the
  property tests, and `serialize::Writer` writes it.
- Section 9 says a `\` delim is written with a newline after it. The
  tokenizer emits the delim only before a newline (4.3.8 reads a backslash
  before the end of the input as a valid escape), so a round trip keeps the
  whitespace token that follows.
- A comment is not a token of the specification. The drivers and `anb::parse`
  skip it as a stream does; `serialize::Writer` writes one as an empty comment
  and lets it separate its neighbours.
- The WPT tests the edition cites for these clauses are adapted as literal
  vectors for what they observe in Syntax 3; see the
  [next section](#wpt-css-syntax-vectors). What they observe through the CSS
  object model, selectors, property validity or `var()` substitution is not
  claimed anywhere on this page.

### Support items without a clause

The `input` and `lexer::protocol` types that are not clauses (the requests, records and errors of the host protocol) and their layout pins in `tests/layout_pins.rs` map to no clause and claim none. The errors (`InputError`, `ProtocolError`, `NumberOverflow`, `LexicalError`) are structs with private causes and `is_*` predicates; their tests are `protocol_errors_name_their_cause_and_describe_it`, `a_digit_count_that_overflows_names_its_counter_and_leaves_the_cursor_unchanged` and `a_number_overflow_describes_itself_and_is_an_error` (`src/lexer/protocol/number.rs`), and the doctests. The performance gate (`tests/lexer_performance.rs`) is a measurement, not a conformance claim. `Offset`, the `limits` module (`Limits`, `DepthExcess`, `Meter`, `Failure`,
`Refused`, `grow`, `copy_str`, `copy_boxed`) and `match_ignore_ascii_case!` are
not defined by Syntax 3, so they map to no clause and claim none. They are
tested in `tests/limits.rs` and `tests/match_ignore_ascii_case.rs`.

The document and stream support that is not a clause claims none either:
`document::TreeBuilder` (adding tokens and groups one at a time, with payloads),
`document::Metrics`, `document::BuildError`, the depth, node and byte limits and
the `DepthExcess::DenyBlock` policy, the navigation (`location`, `parent_group`,
`children`, `list_end`, `node_at_offset`), `Site`, `stream::StreamError` and
`SyntaxError`, and the charging of a `limits::Meter` by a build and by a stream.
Their tests are in `tests/document.rs` (limits, depth, denial, payloads, the
builder, navigation, `a_large_denied_block_is_one_node_charged_for_all_its_bytes`),
`tests/stream.rs` (the error constructors and predicates, sites, text between
sites) and `tests/metering.rs` (the steps of each observation, refusals at every
call, and the storage of a build returned on drop).

The grammar module's support types claim no clause either: `grammar::AtRule`,
`QualifiedRule`, `Declaration` (accessors, ranges, `RuleEnd`), `Failed` (kind,
error, declaration error, extent, how the unit ended, `is_invalid_rule_error`),
`UnitKind`, `Unit`, `anb::AnPlusBError`, `serialize::Adjacency`, and the layout
pins of those types in `tests/layout_pins.rs`. Their accessors are exercised by
the tests above, and `Failed` and the iterators are compared with the clause
through `failure()` in `tests/common/grammar.rs`, which prints every fact.

Sections 7 and 8 define how grammars and style sheets use the syntax. They give
the syntax a CSS meaning and are outside this crate; `surgeist-css` records
their coverage.
