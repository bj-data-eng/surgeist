## <a id="abstract"></a>Abstract

This specification describes user interface related properties and values to style HTML and XML (including XHTML). It includes and extends user interface related features from the properties and values of previous CSS levels. It uses various properties and values to style basic user interface elements in a document.

[CSS](https://www.w3.org/TR/CSS/) is a language for describing the rendering of structured documents (such as HTML and XML) on screen, on paper, etc.

## <a id="intro"></a>1.  Introduction

This module describes CSS properties which enable authors to style user interface related properties and values.

[Section 2.1 of CSS1](https://www.w3.org/TR/REC-CSS1#anchor-pseudo-classes) [\[CSS1\]](#biblio-css1) and [Chapter 18 of CSS2](https://www.w3.org/TR/CSS2/ui.html) [\[CSS21\]](#biblio-css21) introduced several user interface related properties and values. [User Interface for CSS3 (16 February 2000)](https://www.w3.org/TR/2000/WD-css3-userint-20000216) introduced several new user interface related features.

[\[CSS-UI-3\]](#biblio-css-ui-3) was later introduced to incorporate, extend, and supersede these. This specification continues this work, and in turn replaces \[CSS-UI-3\].

### <a id="purpose"></a>1.1.  Purpose

The purpose of this specification is to achieve the following objectives:

- Extend the user interface features in [\[CSS21\]](#biblio-css21) and [\[CSS-UI-3\]](#biblio-css-ui-3)
- Provide additional CSS mechanisms to augment or replace other dynamic presentation related features in HTML.
- Introduce directional navigation properties to assist in the construction of user interfaces which make use of a directional navigation model.

## <a id="outline-props"></a>3.  Outline properties

At times, style sheet authors may want to create outlines around visual objects such as buttons, active form fields, image maps, etc., to make them stand out. Outlines differ from borders in the following ways:

1.  Outlines do not take up space.

2.  <a id="ref-for-ink-overflow-region"></a>

    Outlines contribute to the [ink overflow area](https://www.w3.org/TR/css-overflow-3/#ink-overflow-region) of an element.

3.  Outlines may be non-rectangular.

4.  <a id="ref-for-focus-visible-pseudo"></a>

    UAs often render outlines on elements in the [:focus-visible](https://www.w3.org/TR/selectors-4/#focus-visible-pseudo) state.

The outline properties control the style of these dynamic outlines.

The stacking of the rendering of these outlines is explicitly left up to implementations to provide a better user experience per platform. This supersedes the stacking of outlines as defined in [Appendix E of CSS 2.1](https://www.w3.org/TR/CSS21/zindex.html) [\[CSS21\]](#biblio-css21).

<a id="ref-for-focus-visible-pseudo①"></a>

<strong data-conversion-semantic="advisement">Advisement:</strong> <strong> Keyboard users,
		 in particular people with disabilities
		 who may not be able to interact with the page in any other fashion,
		 depend on the outline being visible
		 on elements in the <a href="https://www.w3.org/TR/selectors-4/#focus-visible-pseudo">:focus-visible</a> state,
		 thus authors must not make the outline invisible on such elements
		 without making sure an alternative highlighting mechanism is provided. </strong>

The rendering of applying transforms to outlines is left explicitly undefined.

The [outline](#propdef-outline) property is a shorthand property and sets all three of [outline-style](#propdef-outline-style), [outline-width](#propdef-outline-width), and [outline-color](#propdef-outline-color). In the ambiguous case where a lone auto value is specified, or if auto is specified together with an <a id="ref-for-propdef-outline-width②"></a>\<'outline-width'\> value, but without an explicit <a id="ref-for-propdef-outline-style②"></a>\<'outline-style'\> or <a id="ref-for-propdef-outline-color②"></a>\<'outline-color'\> value, both <a id="ref-for-propdef-outline-style③"></a>outline-style and <a id="ref-for-propdef-outline-color③"></a>outline-color are set to auto.

<a id="ref-for-propdef-outline-offset"></a>

> <strong data-conversion-semantic="note">Note</strong>
>
> Note: The shorthand purposefully omits the [outline-offset](#propdef-outline-offset) property, which determines the position rather than the appearance of the outline, so that it can cascade independently, as well as for backwards compatibility reasons.

The outline created with the outline properties is drawn "over" a box, i.e., the outline is always on top and doesn’t influence the position or size of the box, or of any other boxes. Therefore, displaying or suppressing outlines does not cause reflow.

Outlines may be non-rectangular. For example, if the element is broken across several lines, the outline should be an outline or minimum set of outlines that encloses all the element’s boxes.

Each part of the outline should be fully connected rather than open on some sides (as borders on inline elements are when lines are broken).

<a id="ref-for-border-edge"></a>

<a id="ref-for-propdef-border-radius"></a>

<a id="ref-for-propdef-corner-shape"></a>

The parts of the outline are not required to be rectangular. To the extent that the outline follows the [border edge](https://www.w3.org/TR/css-box-4/#border-edge), it should follow the [border-radius](https://www.w3.org/TR/css-borders-4/#propdef-border-radius) curve, as well as the [corner-shape](https://www.w3.org/TR/css-borders-4/#propdef-corner-shape).

The position of the outline may be affected by descendant boxes.

<a id="ref-for-ink-overflow-region①"></a>

The dimensions of the drawn outline contribute to the [ink overflow area](https://www.w3.org/TR/css-overflow-3/#ink-overflow-region) of an element.

User agents should use an algorithm for determining the outline that encloses a region appropriate for conveying the concept of focus to the user.

> <strong data-conversion-semantic="note">Note</strong>
>
> Note: This specification does not define the exact position or shape of the outline, but it is typically drawn immediately outside the border box.

> <strong data-conversion-semantic="note">Note</strong>
>
> Note: The outline is the same on all sides. In contrast to borders, there are no outline-top, outline-left, etc. properties.

This specification does not define how multiple overlapping outlines are drawn or how outlines are drawn for boxes that are partially obscured behind other elements.

> <strong data-conversion-semantic="example">Example</strong>
>
> <a id="example-19044d1b"></a> Here’s an example of drawing a thick outline around a BUTTON element:
>
> ```text
> button { outline: thick solid }
> ```
Graphical user interfaces may use outlines around elements to tell the user which element on the page has the focus. These outlines are shown in addition to any borders, and switching outlines on and off should not cause the document to reflow. The focus is the subject of user interaction in a document (e.g. for entering text or selecting a button).

<a id="ref-for-focus-visible-pseudo②"></a>

<a id="ref-for-active-pseudo"></a>

> <strong data-conversion-semantic="example">Example</strong>
>
> <a id="example-0ee013a5"></a> For example, to draw a thick black line around elements in the [:focus-visible](https://www.w3.org/TR/selectors-4/#focus-visible-pseudo) state, and a thick red line when it is in the [:active](https://www.w3.org/TR/selectors-4/#active-pseudo) state, the following rules can be used:
>
> ```text
> :focus-visible  { outline: thick solid black }
> :active { outline: thick solid red }
> ```
> <strong data-conversion-semantic="note">Note</strong>
>
> Note: Since the outline does not affect formatting (i.e., no space is left for it in the box model), it may well overlap other elements on the page.

User agents may enable authors to influence the rendering of auto style outlines via the [outline-color](#propdef-outline-color) property, but this specification does not define how the rendering is impacted (if at all). The [outline-width](#propdef-outline-width) property is ignored when [outline-style](#propdef-outline-style) is auto. User agents may treat auto as solid.

## <a id="resizing"></a>4.  <a id="resizing-and-overflow"></a> Resizing

CSS2.1 provides a mechanism for controlling the appearance of a scrolling mechanism (e.g. scrollbars) on block container elements. This specification adds a mechanism to that for controlling user resizability of elements as well as the ability to specify text overflow behavior.

<a id="ref-for-propdef-height"></a>

<a id="ref-for-propdef-right"></a>

<a id="ref-for-propdef-bottom"></a>

Conforming user agents may, instead of <a id="ref-for-url-value②"></a>\<url\> and <a id="ref-for-typedef-cursor-url-set②"></a>\<url-set\>, support [\<image\>](https://www.w3.org/TR/css-images-3/#typedef-image) which is a superset.

<a id="ref-for-funcdef-image-set"></a>

<a id="ref-for-typedef-image①"></a>

<a id="ref-for-url-value③"></a>

<a id="typedef-cursor-url-set"></a>\<url-set\> is a limited version of [image-set()](https://www.w3.org/TR/css-images-4/#funcdef-image-set), where the [\<image\>](https://www.w3.org/TR/css-images-3/#typedef-image) sub-production is restricted to [\<url\>](https://www.w3.org/TR/css-values-4/#url-value) only.

The UA must support the following image file formats:

- PNG, as defined in [\[PNG\]](#biblio-png)

- <a id="ref-for-natural-size"></a>

  SVG, as defined in [\[SVG11\]](#biblio-svg11), in [secure static mode](https://www.w3.org/TR/SVG2/conform.html#secure-static-mode) [\[SVG2\]](#biblio-svg2), if it has a [natural size](https://www.w3.org/TR/css-images-3/#natural-size).

- <a id="ref-for-propdef-background-image"></a>

  <a id="ref-for-typedef-image②"></a>

  any other non-animated image file format that they support for [\<image\>](https://www.w3.org/TR/css-images-3/#typedef-image) in other properties, such as the [background-image](https://www.w3.org/TR/css-backgrounds-4/#propdef-background-image) property

In addition, the UA should support the following image file formats:

- <a id="ref-for-natural-size①"></a>

  SVG, as defined in [\[SVG11\]](#biblio-svg11), in [secure animated mode](https://www.w3.org/TR/SVG2/conform.html#secure-animated-mode) [\[SVG2\]](#biblio-svg2), if it has a [natural size](https://www.w3.org/TR/css-images-3/#natural-size).

- <a id="ref-for-propdef-background-image①"></a>

  <a id="ref-for-typedef-image③"></a>

  any other animated image file format that they support for [\<image\>](https://www.w3.org/TR/css-images-3/#typedef-image) in other properties, such as the [background-image](https://www.w3.org/TR/css-backgrounds-4/#propdef-background-image) property

<a id="ref-for-natural-size②"></a>

The UA may also support additional file formats, including SVG, as defined in [\[SVG11\]](#biblio-svg11), in secure static mode or secure animated mode [\[SVG2\]](#biblio-svg2), even if it does not have a [natural size](https://www.w3.org/TR/css-images-3/#natural-size).

> <strong data-conversion-semantic="note">Note</strong>
>
> Note: The CSS Working Group initially intended support for all SVG, naturally sized or not. Support for non-naturally sized SVG was downgraded from mandatory to optional due to a lack of implementations.

> <strong data-conversion-semantic="note">Note</strong>
>
> Note: For a number of years, the only file formats supported for cursors in common desktop browsers were the .ico and .cur file formats, as designed by Microsoft. Although this is no longer the case (PNG and SVG have broad support), for compatibility with legacy content, UAs are encouraged to support these, even though the lack of an open specification makes it impossible to have a normative requirement about these formats. Some information on these formats can be found [on Wikipedia](https://en.wikipedia.org/wiki/ICO_%28file_format%29).

<a id="ref-for-default-object-size"></a>

The [default object size](https://www.w3.org/TR/css-images-3/#default-object-size) for cursor images is a UA-defined size that should be based on the size of a typical cursor on the UA’s operating system.

<a id="ref-for-concrete-object-size"></a>

<a id="ref-for-default-sizing-algorithm"></a>

<a id="ref-for-natural-aspect-ratio"></a>

The [concrete object size](https://www.w3.org/TR/css-images-3/#concrete-object-size) is determined using the [default sizing algorithm](https://www.w3.org/TR/css-images-3/#default-sizing-algorithm). If an operating system is <strong>incapable</strong> of rendering a cursor above a given size, cursors larger than that size must be shrunk to within the OS-supported size bounds, while maintaining the cursor image’s [natural aspect ratio](https://www.w3.org/TR/css-images-3/#natural-aspect-ratio), if any.

<a id="ref-for-number-value①"></a>

The optional pair of [\<number\>](https://www.w3.org/TR/css-values-4/#number-value) values give the X and Y coordinates of the exact position within the image which is the pointer position (i.e., the hotspot), as offsets from the left/top of the image.

<a id="ref-for-typedef-image④"></a>

> <strong data-conversion-semantic="note">Note</strong>
>
> Note: This specification does not define how the coordinate systems of the various types of [\<image\>](https://www.w3.org/TR/css-images-3/#typedef-image) are established, and defers these definitions to [\[CSS4-IMAGES\]](#biblio-css4-images).

If the values are omitted, then the natural hotspot defined inside the image resource itself is used. If it has no natural hotspot, the top left corner of the image is used, as if 0 0 were provided.

If the X or Y coordinates of the hotspot (whether specified explicitly or taken from the image) fall outside of the cursor image, they must be clamped (independently) to fit.

<a id="ref-for-typedef-cursor-predefined①"></a>

<a id="valdef-cursor-cursor-predefined"></a>[\<cursor-predefined\>](#typedef-cursor-predefined)

<a id="ref-for-url-value④"></a>

<a id="ref-for-typedef-cursor-predefined②"></a>

The mandatory [\<cursor-predefined\>](#typedef-cursor-predefined) keyword specifies a predefined cursor to use, or the <em>fallback</em> cursor to be used if [\<url\>](https://www.w3.org/TR/css-values-4/#url-value)s were provided and none of them can be successfully used.

<a id="ref-for-typedef-cursor-predefined③"></a>

See [§ 5.1.1.1 Predefined Cursors](#predefined-cursors) for the full set of [\<cursor-predefined\>](#typedef-cursor-predefined) keywords and their meanings.

> <strong data-conversion-semantic="example">Example</strong>
>
> <a id="example-382ff011"></a> Here is an example of using several cursor values.
>
> ```text
> :link,:visited {
>   cursor: url(example.svg),
>     url(hyper.cur),
>     url(hyper.png) 2 3,
>     pointer
> }
> ```
>
> <a id="ref-for-valdef-cursor-pointer"></a>
>
> This example sets the cursor on all hyperlinks (whether visited or not) to an external SVG image to be used as a cursor. If that fails to load, user agents would simply skip to the next value and attempt to use the "hyper.cur" cursor. If that cursor format was also not supported, the UA could attempt to use the "hyper.png" cursor with the explicit hotspot. Finally, if the UA cannot load any of those image cursors, the UA would skip to the last value and render the [pointer](#valdef-cursor-pointer) cursor.

##### <a id="canvas_cursor"></a>5.1.1.2.  Cursor of the canvas

<a id="ref-for-propdef-display"></a>

The document [canvas](https://www.w3.org/TR/CSS21/intro.html#the-canvas) is the infinite surface over which the document is rendered [\[CSS21\]](#biblio-css21). Since no element corresponds to the canvas, in order to allow styling of the cursor when not over any element, the canvas cursor re-uses the root element’s cursor. However, if no boxes are generated for the root element (for example, if the root element has [display: none](https://www.w3.org/TR/css-display-3/#propdef-display)), then the canvas cursor is the platform-dependent default cursor.

<a id="ref-for-propdef-visibility"></a>

<a id="ref-for-propdef-display①"></a>

> <strong data-conversion-semantic="note">Note</strong>
>
> Note: An element might be invisible but still generate boxes. For example, if the element has [visibility: hidden](https://www.w3.org/TR/CSS2/visufx.html#propdef-visibility) but not [display: none](https://www.w3.org/TR/css-display-3/#propdef-display), boxes are generated for it and its cursor is used for the canvas.

### <a id="the-insertion-caret"></a>5.2.  Insertion caret

<a id="ref-for-accept-text-input"></a>

<a id="ref-for-propdef-caret-color"></a>

<a id="ref-for-propdef-caret-animation"></a>

<a id="ref-for-propdef-caret-shape"></a>

<a id="ref-for-insertion-caret"></a>

The <a id="insertion-caret"></a>insertion caret (or “caret” for short) is a visible indicator of the insertion point in an element that [accepts text input](#accept-text-input), where text (and potentially other content) can be inserted by the user. The [caret-color](#propdef-caret-color), [caret-animation](#propdef-caret-animation), and [caret-shape](#propdef-caret-shape) properties give the author some amount of control over the appearance of the [caret](#insertion-caret).

<a id="ref-for-editable-element"></a>

<a id="ref-for-used-value"></a>

<a id="ref-for-propdef-user-select①"></a>

<a id="ref-for-valdef-user-select-none"></a>

<a id="ref-for-dom-contenteditable"></a>

Text or elements are considered to <a id="accept-text-input"></a>accept text input if they are either an [editable element](#editable-element) or a descendent thereof, excluding any such element where the [used value](https://www.w3.org/TR/css-cascade-5/#used-value) of [user-select](#propdef-user-select) is [none](#valdef-user-select-none), as well as subtrees rooted at an HTML element with a <code><a href="https://html.spec.whatwg.org/multipage/interaction.html#dom-contenteditable">contentEditable</a></code> attribute set to `false`.

<a id="ref-for-insertion-caret①"></a>

<a id="ref-for-propdef-caret-color①"></a>

<a id="ref-for-propdef-caret-animation①"></a>

<a id="ref-for-propdef-caret-shape①"></a>

<a id="ref-for-editable-element①"></a>

Some user agents have other user interface mechanisms with a similar appearance, also occasionally referred to as “carets”. For example, some UAs can show a “navigation caret”, which acts similarly to an [insertion caret](#insertion-caret) but can be moved around in non-editable text. The [caret-color](#propdef-caret-color), [caret-animation](#propdef-caret-animation), and [caret-shape](#propdef-caret-shape) properties are not intended to apply to such mechanisms nor outside of [editable elements](#editable-element), though user agents may choose to take them into account. Whether to do so and to what extent is up to the user agent.

<a id="ref-for-propdef-cursor④"></a>

<a id="ref-for-valdef-cursor-auto①"></a>

<a id="ref-for-valdef-cursor-text①"></a>

<a id="ref-for-valdef-cursor-vertical-text①"></a>

> <strong data-conversion-semantic="note">Note</strong>
>
> Note: The cursor image shown when hovering over text when the [cursor](#propdef-cursor) property is [auto](#valdef-cursor-auto), or when hovering over an element where the <a id="ref-for-propdef-cursor⑤"></a>cursor property is [text](#valdef-cursor-text) or [vertical-text](#valdef-cursor-vertical-text), though it sometimes resembles a caret, is not a caret (it’s a cursor).

<a id="ref-for-insertion-caret⑤"></a>

On most platforms and in most UAs, the [insertion caret](#insertion-caret) blinks. This property allows the author to take control over the way the <a id="ref-for-insertion-caret⑥"></a>caret is animated.

<a id="valdef-caret-animation-auto"></a>auto  
<a id="ref-for-insertion-caret⑦"></a>

The UA determines how the [caret](#insertion-caret) should be animated, if at all, as well as the speed of any such animation. It should match platform conventions and settings, and may be adjusted based on context.

<a id="ref-for-insertion-caret⑧"></a>

> <strong data-conversion-semantic="note">Note</strong>
>
> Note: This is typically rendered as a blinking [caret](#insertion-caret). Fading in and out instead of blinking is a variant that appears in some environments.

<a id="valdef-caret-animation-manual"></a>manual  
<a id="ref-for-insertion-caret⑨"></a>

The UA must not animate the [caret](#insertion-caret).

<a id="ref-for-insertion-caret①⓪"></a>

> <strong data-conversion-semantic="note">Note</strong>
>
> Note: This is only about UA-driven animations of the [caret](#insertion-caret). When CSS animations are used to animate the <a id="ref-for-insertion-caret①①"></a>caret color, they apply normally.

<a id="ref-for-insertion-caret①②"></a>

<a id="ref-for-propdef-caret-animation③"></a>

> <strong data-conversion-semantic="note">Note</strong>
>
> Note: It is recommended for authors to stop the [caret](#insertion-caret) from blinking or fading using [caret-animation: manual](#propdef-caret-animation) when applying custom animations using [\[CSS3-ANIMATIONS\]](#biblio-css3-animations), to prevent the UA’s animation and the CSS animation to interfere.

> <strong data-conversion-semantic="note">Note</strong>
>
> Note: See [Guideline 2.3: Seizures: Do not design content in a way that is known to cause seizures](https://www.w3.org/TR/WCAG20/#seizure) [\[WCAG20\]](#biblio-wcag20).

<a id="ref-for-insertion-caret①③"></a>

> <strong data-conversion-semantic="example">Example</strong>
>
> <a id="example-87a611c4"></a> A user who is disturbed by or has adverse reactions to blinking or flashing visuals may want to make all [carets](#insertion-caret) static and non-blinking, regardless of platform defaults or author settings. This can be accomplished with the following rule in the user stylesheet.
>
> ```text
> /* prevent the caret from blinking/flashing */
> :read-write { caret-animation: manual !important; }
> 
> /* prevent changes of caret-color, including animations */
> :read-write { caret-color: auto !important; }
> ```
<a id="ref-for-insertion-caret①④"></a>

UAs that do not have an editable user stylesheet should provide a setting to disable [blinking](https://www.w3.org/TR/WCAG20/#blinksdef), [flashing](https://www.w3.org/TR/WCAG20/#flash-def), and animated [carets](#insertion-caret). UAs that do have an editable user stylesheet may want to provide this setting as well. See [\[WCAG\]](#biblio-wcag) [Guideline 2.2](https://www.w3.org/TR/WCAG20/#time-limits-pause) and [Guideline 2.3](https://www.w3.org/TR/WCAG20/#seizure) for details.

<a id="ref-for-insertion-caret①⑤"></a>

> <strong data-conversion-semantic="example">Example</strong>
>
> <a id="example-37eed1f6"></a> Typically, the [caret](#insertion-caret) blinks on and off. This makes it alternate between 2 colors.
>
> ```text
> textarea {
>   caret-animation: manual;
>   caret-color: blue;
>   animation: caret-alternate 2s step-end infinite;
> }
> @keyframes caret-alternate {
>   50% { caret-color: red; }
> }
> ```

<a id="ref-for-insertion-caret①⑦"></a>

This property allows authors to specify the desired shape of the [insertion caret](#insertion-caret).

Within the context of this definition, <a id="character"></a>character is to be understood as <em>extended grapheme cluster</em>, as defined in [\[UAX29\]](#biblio-uax29), and <a id="visible-character"></a>visible character means a character with a non-zero advance measure.

<a id="valdef-caret-shape-auto"></a>auto  
<a id="ref-for-valdef-caret-shape-block①"></a>

<a id="ref-for-valdef-caret-shape-bar"></a>

<a id="ref-for-insertion-caret①⑧"></a>

The UA determines the shape of the [caret](#insertion-caret). It should match platform conventions, and may be adjusted based on context. For example, if a UA switches between insert mode and overtype mode when the user presses the <em>insert</em> key on their keyboard, it may show a [bar](#valdef-caret-shape-bar) <a id="ref-for-insertion-caret①⑨"></a>caret in insert mode, and a [block](#valdef-caret-shape-block) <a id="ref-for-insertion-caret②⓪"></a>caret in overtype mode.

<a id="valdef-caret-shape-bar"></a>bar  
<a id="ref-for-character"></a>

<a id="ref-for-insertion-caret②①"></a>

The UA must render the [insertion caret](#insertion-caret) as a thin bar placed at the insertion point. This means it is between, before, or after [characters](#character), not over them. It should be perpendicular to the inline progression direction, although UAs may render it slanted when inserting italic or oblique text.

<a id="valdef-caret-shape-block"></a>block  
<a id="ref-for-visible-character"></a>

<a id="ref-for-insertion-caret②②"></a>

The UA must render the [insertion caret](#insertion-caret) as a rectangle overlapping the next [visible character](#visible-character) following the insertion point. If there is no <a id="ref-for-visible-character①"></a>visible character after the insertion point, the UA must render the caret after the last <a id="ref-for-visible-character②"></a>visible character. UAs may render it as a slanted rectangle when inserting italic or oblique text.

<a id="valdef-caret-shape-underscore"></a>underscore  
<a id="ref-for-visible-character③"></a>

<a id="ref-for-under"></a>

<a id="ref-for-insertion-caret②③"></a>

The UA must render the [insertion caret](#insertion-caret) as a thin line [under](https://www.w3.org/TR/css-writing-modes-4/#under) (as defined in [\[CSS-WRITING-MODES-3\]](#biblio-css-writing-modes-3)) the next [visible character](#visible-character) following the insertion point. If there is no <a id="ref-for-visible-character④"></a>visible character after the insertion point, the UA must render the caret after the last <a id="ref-for-visible-character⑤"></a>visible character.

<a id="ref-for-valdef-caret-shape-block②"></a>

<a id="ref-for-valdef-caret-shape-underscore"></a>

<a id="ref-for-insertion-caret②④"></a>

<a id="ref-for-visible-character⑥"></a>

The width of the [block](#valdef-caret-shape-block) and [underscore](#valdef-caret-shape-underscore) [carets](#insertion-caret) should be the advance measure of the next [visible character](#visible-character) after the insertion point, or 1ch if there is no next <a id="ref-for-visible-character⑦"></a>visible character or if this information is impractical to determine.

<a id="ref-for-insertion-caret②⑤"></a>

<a id="ref-for-writing-mode"></a>

<a id="ref-for-elementdef-textPath"></a>

When determining the orientation and appearance of the [caret](#insertion-caret), UAs must take into account the [writing mode](https://www.w3.org/TR/css-writing-modes-4/#writing-mode) [\[CSS-WRITING-MODES-3\]](#biblio-css-writing-modes-3) and must apply transformations [\[CSS-TRANSFORMS-1\]](#biblio-css-transforms-1). If the edited text is laid out on a path, for instance by using the SVG <code><a href="https://www.w3.org/TR/SVG2/text.html#elementdef-textPath">textPath</a></code> element, UAs should also account for this.

<a id="ref-for-valdef-caret-shape-bar①"></a>

<a id="ref-for-valdef-caret-shape-underscore①"></a>

<a id="ref-for-insertion-caret②⑥"></a>

<a id="ref-for-valdef-caret-shape-auto"></a>

The thickness of [bar](#valdef-caret-shape-bar) and [underscore](#valdef-caret-shape-underscore) [carets](#insertion-caret)—​as well as that of [auto](#valdef-caret-shape-auto) <a id="ref-for-insertion-caret②⑦"></a>carets with a similar rendering—​is determined by the user agent. When practical, the user agent should choose a thickness that ensures the <a id="ref-for-insertion-caret②⑧"></a>caret remains visible even if it has been scaled down via means such as transformations [\[CSS-TRANSFORMS-1\]](#biblio-css-transforms-1).

<a id="ref-for-scrollable-overflow-region"></a>

<a id="ref-for-scrollport"></a>

When there is not enough room at the end of a line to display the caret positioned there, the user agents should still display it, even if that means means painting past the bounds of the [scrollable overflow area](https://www.w3.org/TR/css-overflow-3/#scrollable-overflow-region); user agents may impose limits on this and clip as necessary. User agents may also visually reposition a caret in order to display it within the [scrollport](https://www.w3.org/TR/css-overflow-3/#scrollport) if it would otherwise be invisible.

<a id="ref-for-insertion-caret②⑨"></a>

The stacking position of the [caret](#insertion-caret) is left undefined within the following constraints:

- <a id="ref-for-insertion-caret③⓪"></a>

  The [caret](#insertion-caret) must not be obscured by the background of the element.

- <a id="ref-for-insertion-caret③①"></a>

  <a id="ref-for-valdef-caret-shape-block③"></a>

  UAs must render [block](#valdef-caret-shape-block) [carets](#insertion-caret) so that the character it overlaps with is not obscured by the <a id="ref-for-insertion-caret③②"></a>caret.

The user agent automatically determines which element to navigate the focus to in response to directional navigational input.

<a id="ref-for-typedef-id①"></a>

<a id="typedef-id"></a>[\<id\>](#typedef-id)

<a id="ref-for-typedef-id②"></a>

The [\<id\>](#typedef-id) value is an ID selector [\[SELECT\]](#biblio-select). In response to directional navigation input corresponding to the property, the focus is navigated to the first element in tree order matching the selector.

If this refers to the currently focused element, the directional navigation input respective to the nav- property is ignored — there is no need to refocus the same element.

If no element matches the selector, the user agent automatically determines which element to navigate the focus to.

<a id="ref-for-focus-pseudo"></a>

If the focus is navigated to an element that was not otherwise focusable, it becomes focusable only as the result of this directional navigation, and the [:focus](https://www.w3.org/TR/selectors-4/#focus-pseudo) pseudo-class matches the element while it is focused as such.

> <strong data-conversion-semantic="note">Note</strong>
>
> Note: there were other options under consideration for such "not otherwise focusable" elements, including focus to the next otherwise focusable element in the document tree (including descendants of such a not otherwise focusable element). Input on such other options is welcome and explicitly solicited, especially from implementation experiences and author experience using the directional navigation properties in their content.

<a id="ref-for-typedef-target-name①"></a>

<a id="typedef-target-name"></a>[\<target-name\>](#typedef-target-name)

<a id="ref-for-string-value"></a>

The \<target-name\> parameter indicates the target frame for the focus navigation. It is a [\<string\>](https://www.w3.org/TR/css-values-4/#string-value) and it MUST NOT start with the underscore "\_" character. Error handling: if it does start with an underscore, "\_parent" navigates to the parent frame, "\_root" is treated as root, and other values navigate to a frame by that name if it exists. If the specified target frame does not exist, the parameter will be treated as the keyword current, which means to simply use the frame that the element is in. The keyword root indicates that the user agent should target the full window.

User agents for devices with directional navigation keys respond by navigating the focus according to four respective nav-\* directional navigation properties (nav-up, nav-right, nav-down, nav-left). This specification does not define which keys of a device are directional navigational keys.

> <strong data-conversion-semantic="note">Note</strong>
>
> Note: Typical personal computers have keyboards with four arrow keys. One possible implementation would be to use those four arrow keys for directional navigation. For accessibility and user convenience, user agents should allow configuration of which keys on a keyboard are used for directional navigation.

> }

>   top:100%; left:50%;
>   nav-right:#b4; nav-left:#b2;
>   nav-down:#b4; nav-up:#b2;

Users may use the ime-mode property only for repair use cases where they have to work around bad sites and legacy implementations, e.g. with a user style sheet rule like:

<a id="ref-for-valdef-user-select-all②"></a>

>
> Note: As of the time of writing, experimental implementations do not all behave like this. Firefox does. IE does not restrict selections started outside of the element from going into it at all. Another difference is that in Chrome and Safari, if the user attempts to start a selection inside a [user-select: none](#propdef-user-select), and to end the selection out of it, a selection will be created from the boundary of the element to the user-designated end point. Firefox and Internet Explorer behave as prescribed in this specification and do not create a selection at all.

The UA must allow selections to extend across this element, and must exclude this element from such a selection. An exception is made for UAs which do not support multiple ranges per selection, and they may include this element. If the element has descendants on which the [used value](https://www.w3.org/TR/css-cascade-5/#used-value) of [user-select](#propdef-user-select) is not [none](#valdef-user-select-none), these descendants must be included in a selection extending across the element. <strong data-conversion-semantic="note">Note:</strong> This specification makes no normative requirement about the behavior of the clipboard. However, UAs are encouraged to keep the visual selection consistent with what would get copied to the clipboard when copying. Copying text that does not appear to be selected, or vice versa, is highly confusing to users.

<a id="ref-for-propdef-user-select⑨"></a>

<a id="ref-for-valdef-user-select-none①⓪"></a>

Attempting to start a selection in an element where [user-select](#propdef-user-select) is [none](#valdef-user-select-none), such as by clicking in it or starting a drag in it, must not cause a pre-existing selection to become unselected or to be affected in any way.

<a id="ref-for-propdef-user-select①⓪"></a>

<a id="ref-for-valdef-user-select-none①①"></a>

As [user-select](#propdef-user-select) is a UI convenience mechanism, not a copy protection mechanism, the UA may provide an alternative way for the user to explicitly select the text even when <a id="ref-for-propdef-user-select①①"></a>user-select is [none](#valdef-user-select-none).

<a id="ref-for-valdef-user-select-none①②"></a>

> <strong data-conversion-semantic="note">Note</strong>
>
> Note: [none](#valdef-user-select-none) is not a copy protection mechanism, and using it as such is ineffective: user agents are allowed to provide ways to bypass it, it will have no effect on legacy user agents that do not support it, and the user can disable it through the user style sheet or equivalent mechanisms on UAs that do anyway. Instead, <a id="ref-for-valdef-user-select-none①③"></a>none is meant to make it easier for the user to select the content they want by letting the author disable selection on UI elements that are not useful to select. Tools such as CSS validators, linters, or in-browser developer tools are encouraged to use heuristics to detect and warn against incorrect or abusive usage that would hamper usability or violate common user expectations.

<a id="ref-for-propdef-user-select①②"></a>

> <strong data-conversion-semantic="note">Note</strong>
>
> Authors should be careful about not constraining the user unnecessarily. For example, setting [user-select: none](#propdef-user-select) on the root element, and relaxing that restriction on a handful of elements the author judges useful to select can be frustrating to users:
> - Clicking in empty areas to undo the current selection will no longer be effective
>
> - The author may have overlooked some areas which should be selectable
>
> - Areas may be added later to the page without remembering to make them selectable
>
> - The user may want to select pieces of text other than the main content, for instance to look them up in a dictionary or in some translation tool, or to look for warnings and error messages in a search engine…
>
> <a id="ref-for-propdef-user-select①③"></a>
>
> Instead, a good practice is for authors is to selectively apply [user-select: none](#propdef-user-select) to elements which seem likely to be accidentally selected when doing so would interfere with the more likely intended action. Accidentally leaving parts of the page that are unlikely to be interacted with selectable will likely cause much less frustration to users than the opposite.

<a id="valdef-user-select-contain"></a>contain  
UAs must not allow a selection which is started in this element to be extended outside of this element.

A selection started outside of this element must not end in this element. If the user attempts to create such a selection, the UA must instead end the selection range at the element boundary.

The UA must allow selections to extend across this element, and such selections must include the content of the element.

<a id="ref-for-valdef-user-select-contain③"></a>

<a id="ref-for-the-textarea-element①"></a>

> <strong data-conversion-semantic="note">Note</strong>
>
> Note: At the time of writing, experimental implementations behave differently from each other about selections started outside and selections going into the element. The behavior can be observed even on browsers that do not explicitly support [contain](#valdef-user-select-contain) by trying to select into a <code><a href="https://html.spec.whatwg.org/multipage/form-elements.html#the-textarea-element">textarea</a></code> or a contenteditable element.

> <strong data-conversion-semantic="note">Note</strong>
>
> Note: This was initially introduced as an experimental feature in Internet Explorer, under the name `user-select: element`.

<a id="valdef-user-select-all"></a>all  
<a id="ref-for-valdef-user-select-all③"></a>

<a id="ref-for-propdef-user-select①④"></a>

<a id="ref-for-used-value①⑤"></a>

The content of the element must be selected atomically: If a selection would contain part of the element, then the selection must contain the entire element including all its descendants. If the element is selected and the [used value](https://www.w3.org/TR/css-cascade-5/#used-value) of [user-select](#propdef-user-select) on its parent is [all](#valdef-user-select-all), then the parent must be included in the selection, recursively.

<a id="ref-for-used-value①⑥"></a>

<a id="ref-for-propdef-user-select①⑤"></a>

<a id="ref-for-valdef-user-select-all④"></a>

If this element has descendants on which the [used value](https://www.w3.org/TR/css-cascade-5/#used-value) of [user-select](#propdef-user-select) is not [all](#valdef-user-select-all) and if a selection is entirely contained in these descendants, then the selection is not extended to include this whole element.

> <strong data-conversion-semantic="note">Note</strong>
>
> Note: Selections can include more than just text and extend over images, tables, videos, etc. The behavior when copying and pasting such selections is out of scope for this specification.

```text
button, meter, progress, select { user-select: none; }
```

Some [host language](https://www.w3.org/TR/selectors-4/#host-language) features can be activated when a user "shows interest" in an element. Exactly what this means is up to the <a id="ref-for-host-language②"></a>host language and [user agent](https://infra.spec.whatwg.org/#user-agent) (for example, the HTML <code><a>interestfor</a></code> attribute), but a common property of such features is that "interest" shouldn’t be gained or lost <em>instantly</em>.

For example, if "interest" can be shown by hovering the cursor over an element, briefly passing the cursor over the element while moving the cursor over the page should not (at least by default) indicate "interest"—​that could result in UI confusingly popping up and disappearing while the user is performing unrelated tasks.

Similarly, once interest has been shown, it should not (at least by default) <em>lose</em> interest instantaneously either. Again, as an example, if the user "shows interest" in a link by hovering the cursor over it, causing a child popup list to appear next to it, moving the cursor from the link to the popup likely involves briefly leaving both the link and the list, but shouldn’t cause the list to "lose interest" and close the popup.

While the way most elements in a document look can be fully controlled by CSS, [widgets](#widget) are typically rendered by UAs using native UI controls of the host operating system, which can neither be replicated nor styled using CSS.

<a id="ref-for-replaced-element"></a>

<a id="ref-for-native-appearance"></a>

The term <a id="widget"></a>widget in this specification denotes [replaced](https://www.w3.org/TR/css-display-4/#replaced-element) elements that can have <a id="native-appearance"></a>native appearance, meaning that they are rendered like analogous native widgets or controls of the host operating system or platform, or with a look and feel not otherwise expressible in CSS. It is up to the host language (e.g., HTML [\[HTML\]](#biblio-html)) to define which elements can have [native appearance](#native-appearance).

<a id="ref-for-propdef-appearance①"></a>

<a id="ref-for-native-appearance①"></a>

<a id="ref-for-widget①"></a>

This specification introduces the [appearance](#propdef-appearance) property to provide some control over this behavior. In particular, using <a id="ref-for-propdef-appearance②"></a>appearance: none allows authors to suppress the [native appearance](#native-appearance) of [widgets](#widget), giving them a <a id="primitive-appearance"></a>primitive appearance where CSS can be used to restyle them.

<a id="ref-for-propdef-appearance③"></a>

<a id="ref-for-widget②"></a>

<a id="ref-for-native-appearance②"></a>

<a id="ref-for-primitive-appearance"></a>

Using [appearance: base](#propdef-appearance) gives [widgets](#widget) a <a id="base-appearance"></a>base appearance. <a id="ref-for-widget③"></a>Widgets in base appearance have their [native appearance](#native-appearance) suppressed where CSS can be used to restyle them, just like [primitive appearance](#primitive-appearance), but also have default styles which are usable and interoperable. This is unlike <a id="ref-for-primitive-appearance①"></a>primitive appearance which can cause some <a id="ref-for-widget④"></a>widgets to disappear completely.

A widget can have some style sheet associated with it and those styles can change based on whether the widget has a base appearance. Native appearance and primitive appearance should have the same styles.

> <strong data-conversion-semantic="issue">Issue</strong>
>
> <a id="issue-0c60b9fd"></a> appearance:base is not ready to ship until its stylesheet has been fully defined in the HTML specification, and implemented accordingly for all HTML form controls.

> <strong data-conversion-semantic="note">Note</strong>
>
> Note on the history of this feature
>
> <a id="ref-for-valdef-appearance-none①"></a>
>
> This previously existed in prefixed form in most browsers. Before standardization, in addition to [none](#valdef-appearance-none), the possible values were a very long list of all the ways an element could look; each value being responsible for giving form controls their specific look and feel. This list was different across browsers.
>
> The CSS Working Group concluded this was impractical to standardize, in part because many values applied to pseudo-elements that other browsers don’t have, as they construct form elements differently, and which should not be standardized, since the ability to make form controls look substantially different on different platforms should be preserved.
>
> Also, the ability to turn any arbitrary element (including any form control) into any (other) arbitrary form control is considered a misfeature.
>
> <a id="ref-for-native-appearance③"></a>
>
> Instead, the design being specified is based on just having an "auto" value that makes form controls look like whatever they need, and a "none" value that suppresses [native appearance](#native-appearance).
>
> However, there is evidence that this alone is not web compatible, due in part to uses such as:
>
> ```text
> input { appearance: none; }
> input[type=checkbox] { appearance: checkbox; }
> ```
>
> The design specified here is a compromise between the two, preserving the simplicity of the none \| auto model while maintaining compatibility with existing content via a few additional keywords.
>
> The precise list of keywords needed for compatibility and their exact behavior is likely to be refined in a future version of this specification to better handle compatibility with existing content. The CSS-WG welcomes relevant feedback.

User agents may [disregard](#disregard) some CSS properties used to size and paint the contents of [widgets](#widget) rendered with their [native appearance](#native-appearance) to ensure that the intended appearance is preserved, or because these properties may not be meaningful for the chosen appearance.

<a id="ref-for-apply"></a>

<a id="ref-for-computed-value③"></a>

<a id="ref-for-disregard①"></a>

<a id="disregard"></a>Disregarding a property means that the user agent treats it as if it didn’t [apply to](https://www.w3.org/TR/css-cascade-5/#apply) the widget in question. Nevertheless, unless an explicit exception is specified (for compatibility reasons), the user agent must still determine the [computed value](https://www.w3.org/TR/css-cascade-5/#computed-value) of any [disregarded](#disregard) property according to the usual rules.

<a id="ref-for-native-appearance⑨"></a>

In more detail, the rules for disregarding properties for [natively rendered](#native-appearance) widgets are:

- <a id="ref-for-native-appearance①⓪"></a>

  <a id="ref-for-widget①⑨"></a>

  <a id="ref-for-propdef-box-shadow"></a>

  <a id="ref-for-propdef-filter"></a>

  <a id="ref-for-propdef-transform"></a>

  <a id="ref-for-sizing-property"></a>

  CSS properties that impact the box sizing or position of the widget’s box (such as the [sizing properties](https://www.w3.org/TR/css-sizing-3/#sizing-property)), or their visual appearance outside of the box (such as [transform](https://www.w3.org/TR/css-transforms-1/#propdef-transform), [filter](https://www.w3.org/TR/filter-effects-1/#propdef-filter) or [box-shadow](https://www.w3.org/TR/css-borders-4/#propdef-box-shadow)), must be applied to [widgets](#widget) rendered with their [native appearance](#native-appearance). The widget’s box participates in the rest of layout like any other replaced element.

- <a id="ref-for-propdef-margin"></a>

  <a id="ref-for-propdef-border"></a>

  <a id="ref-for-propdef-padding"></a>

  <a id="ref-for-propdef-box-sizing①"></a>

  Properties that affect the internal box model sizing of the widget’s box (such as [box-sizing](https://www.w3.org/TR/css-sizing-3/#propdef-box-sizing), [padding](https://www.w3.org/TR/css-box-4/#propdef-padding), [border](https://www.w3.org/TR/css-borders-4/#propdef-border) or [margin](https://www.w3.org/TR/css-box-4/#propdef-margin)) may be disregarded when needed.

- <a id="ref-for-propdef-background-color①"></a>

  Other properties that affect painting (like [background-color](https://www.w3.org/TR/css-backgrounds-3/#propdef-background-color)) may be disregarded when needed.

- User agents should take into account CSS properties that affect writing modes or font-related properties when possible, when rendering text within the widget.

- <a id="ref-for-propdef-object-fit"></a>

  The [object-fit](https://www.w3.org/TR/css-images-4/#propdef-object-fit) property does not apply.

<a id="ref-for-propdef-border①"></a>

<a id="ref-for-propdef-padding①"></a>

<a id="ref-for-native-appearance①①"></a>

> <strong data-conversion-semantic="example">Example</strong>
>
> <a id="example-664d74be"></a> Some user agents respect the [border](https://www.w3.org/TR/css-borders-4/#propdef-border) and [padding](https://www.w3.org/TR/css-box-4/#propdef-padding) CSS properties for a \<select\> rendered with [native appearance](#native-appearance), but not for \<input type=checkbox\>.

Native rendering of widgets may overflow the size of its box if its intrinsic sizing exceeds that size.

<a id="ref-for-legacy-name-alias"></a>

<a id="ref-for-propdef-appearance⑥"></a>

For compatibility with legacy content, UAs must also support <a id="propdef--webkit-appearance"></a>-webkit-appearance as a [legacy name alias](https://www.w3.org/TR/css-cascade-5/#legacy-name-alias) of [appearance](#propdef-appearance).

#### <a id="appearance-disabling-properties"></a>7.2.1.  Properties Disabling Native Appearance

<a id="ref-for-cascade-origin-author"></a>

<a id="ref-for-native-appearance①②"></a>

<a id="ref-for-widget②⓪"></a>

<a id="ref-for-cascaded-value"></a>

<a id="ref-for-valdef-all-revert"></a>

<a id="ref-for-valdef-all-revert-layer"></a>

<a id="ref-for-property-that-disables-native-appearance-for-widgets"></a>

<a id="ref-for-devolved①"></a>

<a id="ref-for-primitive-appearance③"></a>

Certain properties, when declared in the [Author Origin](https://www.w3.org/TR/css-cascade-5/#cascade-origin-author), will disable the [native appearance](#native-appearance) of certain [widgets](#widget). Specifically, if all the declarations of the <a id="ref-for-cascade-origin-author①"></a>Author Origin pertaining to such a <a id="ref-for-widget②①"></a>widget are cascaded and a [cascaded value](https://www.w3.org/TR/css-cascade-5/#cascaded-value) exists—​after having rolled back any number [revert](https://www.w3.org/TR/css-cascade-5/#valdef-all-revert) or [revert-layer](https://www.w3.org/TR/css-cascade-5/#valdef-all-revert-layer) values—​for any [property that disables native appearance for widgets](#property-that-disables-native-appearance-for-widgets), then that <a id="ref-for-widget②②"></a>widget is rendered as a [devolved widget](#devolved). The rendering of a <a id="devolved"></a>devolved widget is identical to that of the <a id="ref-for-widget②③"></a>widget in its [primitive appearance](#primitive-appearance), except when specified otherwise by the host language.

#### <a id="appearance-decorative"></a>7.2.2.  Effects of [appearance](#propdef-appearance) on Decorative Aspects of Elements

<a id="ref-for-widget②④"></a>

<a id="ref-for-native-appearance①③"></a>

<a id="ref-for-primitive-appearance④"></a>

<a id="ref-for-propdef-appearance⑧"></a>

All decorative visual aspects of a [widget](#widget) which are not caused by a CSS style rule must be suppressed when the appearance is changed from [native](#native-appearance) to [primitive](#primitive-appearance) using [appearance](#propdef-appearance), even if the UA’s internal representation for this element was composed of multiple elements or pseudo-elements combined together.

<a id="ref-for-the-select-element②"></a>

<a id="ref-for-propdef-appearance⑨"></a>

<a id="ref-for-the-select-element③"></a>

<a id="ref-for-valdef-appearance-none⑤"></a>

> <strong data-conversion-semantic="example">Example</strong>
>
> <a id="example-8d8c62ea"></a> For example, the [\[HTML\]](#biblio-html) <code><a href="https://html.spec.whatwg.org/multipage/form-elements.html#the-select-element">select</a></code> element is often rendered with an arrow on the right side indicating that the list will be expanded if the element is clicked. If the computed value of [appearance](#propdef-appearance) on a <code><a href="https://html.spec.whatwg.org/multipage/form-elements.html#the-select-element">select</a></code> element is [none](#valdef-appearance-none), this must disappear.

<a id="ref-for-widget②⑤"></a>

<a id="ref-for-propdef-appearance①⓪"></a>

<a id="ref-for-valdef-appearance-none⑥"></a>

UAs should include in their user agent stylesheet style rules to give [widgets](#widget) a recognizable shape when [appearance](#propdef-appearance) is [none](#valdef-appearance-none).

> <strong data-conversion-semantic="note">Note</strong>
>
> Note: Authors may therefore need to override these UA style rules to get the styling they intended.

<a id="ref-for-propdef-all"></a>

<a id="ref-for-widget②⑥"></a>

> <strong data-conversion-semantic="advisement">Advisement</strong>
>
> Authors may find it convenient to use [all: unset](https://www.w3.org/TR/css-cascade-5/#propdef-all) to get fully unstyled [widgets](#widget), which they can then style as they want without interference from the user agent’s stylesheet. However, this also suppresses the focus indicators provided by the same UA stylesheet. In order to avoid damaging accessibility, authors who do so should restore a focus indicator, for instance, by using :focus-visible { outline: auto; }.

<a id="ref-for-propdef-appearance①①"></a>

#### <a id="appearance-semantics"></a>7.2.3.  Effects of [appearance](#propdef-appearance) on Semantic Aspects of Elements

<a id="ref-for-primitive-appearance⑤"></a>

<a id="ref-for-widget②⑦"></a>

<a id="ref-for-devolved②"></a>

When showing the [primitive appearance](#primitive-appearance) of a [widget](#widget) or its [devolved](#devolved) state, user agents must preserve aspects of the <a id="ref-for-widget②⑧"></a>widget which are necessary to operate the <a id="ref-for-widget②⑨"></a>widget with its original semantics. The UA may, however, give them a different look and feel as long as it remains possible to operate the <a id="ref-for-widget③⓪"></a>widget. Aspects of a <a id="ref-for-widget③①"></a>widget which are merely needed to observe the state the <a id="ref-for-widget③②"></a>widget is in and are not needed to operate it should be suppressed as well when the same information can be conveyed using ordinary CSS. Document languages should specify for each <a id="ref-for-widget③③"></a>widget that they define what needs to be preserved.

<a id="ref-for-propdef-appearance①②"></a>

<a id="ref-for-valdef-appearance-none⑦"></a>

> <strong data-conversion-semantic="example">Example</strong>
>
> <a id="example-0abef2f6"></a> For example, the slider of an `<input type=range>` is preserved (or replaced by an equivalent mechanism) even if [appearance](#propdef-appearance) is [none](#valdef-appearance-none), as it would otherwise not be possible to change the value of the range with the mouse or touchscreen.
>
> <a id="ref-for-checked-pseudo"></a>
>
> On the other hand, the check mark in an `<input type=checkbox checked>` must be suppressed, as it merely indicates the state the element is in, which can be styled in different ways using the [:checked](https://www.w3.org/TR/selectors-4/#checked-pseudo) selector.

The behavior and semantics of elements remain defined by the document language, and are not influenced by this property.

<a id="ref-for-propdef-appearance①③"></a>

> <strong data-conversion-semantic="example">Example</strong>
>
> <a id="example-9dc58b5f"></a> For example, regardless of the computed value of [appearance](#propdef-appearance):
>
> - Elements which can be in different states keep this ability, and the relevant pseudo-classes match as usual.
>
> - <a id="ref-for-the-option-element"></a>
>
>   <a id="ref-for-the-select-element④"></a>
>
>   If a <code><a href="https://html.spec.whatwg.org/multipage/form-elements.html#the-select-element">select</a></code> element is activated, the UI to choose one of the associated <code><a href="https://html.spec.whatwg.org/multipage/form-elements.html#the-option-element">option</a></code> elements is shown (although it may look different).
>
> - Event handlers attached to the element trigger as usual.

Conversely, changing the appearance of an element must not cause it to acquire the semantics, pseudo-classes, event handlers, etc. that are typical of the element whose appearance it acquires.

<a id="ref-for-enabled-pseudo"></a>

<a id="ref-for-disabled-pseudo"></a>

<a id="ref-for-the-div-element"></a>

<a id="ref-for-propdef-appearance①④"></a>

> <strong data-conversion-semantic="example">Example</strong>
>
> <a id="example-84da96a5"></a> For example, neither [:enabled](https://www.w3.org/TR/selectors-4/#enabled-pseudo) nor [:disabled](https://www.w3.org/TR/selectors-4/#disabled-pseudo) match on a <code><a href="https://html.spec.whatwg.org/multipage/grouping-content.html#the-div-element">div</a></code> styled with [appearance: button](#propdef-appearance). The ability for an element to be focused is also not changed by the <a id="ref-for-propdef-appearance①⑤"></a>appearance property.

### <a id="control-specific-rules"></a>7.3.  Control-Specific Rules

> <strong data-conversion-semantic="issue">Issue</strong>
>
> <a id="issue-0b89ac4a"></a> Maybe some or all of this section should be moved to the [\[HTML\]](#biblio-html) spec. at some point.

<a id="ref-for-propdef-appearance①⑥"></a>

<a id="ref-for-valdef-appearance-auto⑥"></a>

<a id="ref-for-propdef-border②"></a>

> <strong data-conversion-semantic="issue">Issue</strong>

#### <a id="input-rules"></a>7.3.1.  Single-Line Text Input Controls

<a id="ref-for-propdef-appearance①⑨"></a>

<a id="ref-for-valdef-appearance-auto⑧"></a>

When [appearance](#propdef-appearance) is [auto](#valdef-appearance-auto), single-line text input controls such as [\[HTML\]](#biblio-html) `<input type=text>` must be rendered so that:

- <a id="ref-for-content-edge"></a>

  The content is clipped in the inline direction to the [content edge](https://www.w3.org/TR/css-box-4/#content-edge)

- <a id="ref-for-padding-edge"></a>

  The content is clipped in the block direction to the [padding edge](https://www.w3.org/TR/css-box-4/#padding-edge)

- The content is vertically centered

- The content does not wrap

- <a id="ref-for-propdef-text-overflow①"></a>

  <a id="ref-for-propdef-overflow②"></a>

  The [text-overflow](https://www.w3.org/TR/css-overflow-4/#propdef-text-overflow) property applies regardless of the value of the [overflow](https://www.w3.org/TR/css-overflow-3/#propdef-overflow) property

## <a id="w3c-conformance"></a> Conformance

### <a id="w3c-conventions"></a> Document conventions

Conformance requirements are expressed with a combination of descriptive assertions and RFC 2119 terminology. The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in the normative parts of this document are to be interpreted as described in RFC 2119. However, for readability, these words do not appear in all uppercase letters in this specification.

All of the text of this specification is normative except sections explicitly marked as non-normative, examples, and notes. [\[RFC2119\]](#biblio-rfc2119)

Examples in this specification are introduced with the words “for example” or are set apart from the normative text with `class="example"`, like this:

> <strong data-conversion-semantic="example">Example</strong>
>
> <a id="w3c-example"></a>
>
> This is an example of an informative example.

Informative notes begin with the word “Note” and are set apart from the normative text with `class="note"`, like this:

> <strong data-conversion-semantic="note">Note</strong>
>
> Note, this is an informative note.

Advisements are normative sections styled to evoke special attention and are set apart from other normative text with `<strong class="advisement">`, like this: <strong data-conversion-semantic="advisement">Advisement:</strong> <strong> UAs MUST provide an accessible alternative. </strong>

### <a id="w3c-conformance-classes"></a> Conformance classes

Conformance to this specification is defined for three conformance classes:

style sheet  
A [CSS style sheet](https://www.w3.org/TR/CSS21/conform.html#style-sheet).

renderer  
A [UA](https://www.w3.org/TR/CSS21/conform.html#user-agent) that interprets the semantics of a style sheet and renders documents that use them.

authoring tool  
A [UA](https://www.w3.org/TR/CSS21/conform.html#user-agent) that writes a style sheet.

A style sheet is conformant to this specification if all of its statements that use syntax defined in this module are valid according to the generic CSS grammar and the individual grammars of each feature defined in this module.

A renderer is conformant to this specification if, in addition to interpreting the style sheet as defined by the appropriate specifications, it supports all the features defined by this specification by parsing them correctly and rendering the document accordingly. However, the inability of a UA to correctly render a document due to limitations of the device does not make the UA non-conformant. (For example, a UA is not required to render color on a monochrome monitor.)

An authoring tool is conformant to this specification if it writes style sheets that are syntactically correct according to the generic CSS grammar and the individual grammars of each feature in this module, and meet all other conformance requirements of style sheets as described in this module.

### <a id="w3c-partial"></a> Partial implementations

So that authors can exploit the forward-compatible parsing rules to assign fallback values, CSS renderers <strong>must</strong> treat as invalid (and [ignore as appropriate](https://www.w3.org/TR/CSS21/conform.html#ignore)) any at-rules, properties, property values, keywords, and other syntactic constructs for which they have no usable level of support. In particular, user agents <strong>must not</strong> selectively ignore unsupported component values and honor supported values in a single multi-value property declaration: if any value is considered invalid (as unsupported values must be), CSS requires that the entire declaration be ignored.

#### <a id="w3c-conform-future-proofing"></a> Implementations of Unstable and Proprietary Features

To avoid clashes with future stable CSS features, the CSSWG recommends [following best practices](https://www.w3.org/TR/CSS/#future-proofing) for the implementation of [unstable](https://www.w3.org/TR/CSS/#unstable) features and [proprietary extensions](https://www.w3.org/TR/CSS/#proprietary-extension) to CSS.

### <a id="w3c-testing"></a> Non-experimental implementations

Once a specification reaches the Candidate Recommendation stage, non-experimental implementations are possible, and implementors should release an unprefixed implementation of any CR-level feature they can demonstrate to be correctly implemented according to spec.

To establish and maintain the interoperability of CSS across implementations, the CSS Working Group requests that non-experimental CSS renderers submit an implementation report (and, if necessary, the testcases used for that implementation report) to the W3C before releasing an unprefixed implementation of any CSS features. Testcases submitted to W3C are subject to review and correction by the CSS Working Group.

Further information on submitting testcases and implementation reports can be found from on the CSS Working Group’s website at [https&#x3A;&#x2F;&#x2F;www&#x2E;w3&#x2E;org&#x2F;Style&#x2F;CSS&#x2F;Test&#x2F;](https://www.w3.org/Style/CSS/Test/)&#x2E; Questions should be directed to the [public-css-testsuite@w3.org](https://lists.w3.org/Archives/Public/public-css-testsuite) mailing list.
